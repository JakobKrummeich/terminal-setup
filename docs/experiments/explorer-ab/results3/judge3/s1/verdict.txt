reasoning: Both solutions deliver a working vertical slice of the quiz phase across domain, hub protocol, persistence, and frontend, but they differ in where invariants live and how deeply the slice is proven. Solution 1 models `QuizContent` as a Domain value object whose `Of` factory enforces invariants and throws `InvariantViolationException`, so an invalid quiz cannot exist at runtime; Solution 2 places `QuizContent` in Application/Content as a plain record with validation living only in the Host loader, so invalid instances remain constructible from any other call path. Solution 1's test coverage is materially broader: an explicit JSON anonymity test, a `quiz_answers` schema test, a `BackendRestartTests` case proving tallies survive restart and reconnect, and a full quiz loop in `HubProtocolTests` — the restart/reconnect case is exactly the kind of regression that a persistence-backed tally is prone to. Solution 2 also omits the roster-membership check in `Session.ChooseQuizAnswer`, which lets a non-member answer, and it leaves `config/quiz.json` at fewer than the five questions the backlog criterion calls for. Solution 2 is better in two concrete respects: converting the static mappers into injected instance classes is cleaner DI than Solution 1's habit of threading `QuizContent` as an extra parameter through statics, and its `QuizContentValidation` collects all problems with JSON paths, which is a genuinely nicer operator experience than fail-fast. It also makes the facilitator view more protocol-complete by including `answerTallies`/`answeredCount`, whereas Solution 1 defers that to Task 14 (documented, but still a gap). Against that, Solution 2 renames the existing `isAdvancing` to `isInFlight` and deletes several existing advance-phase tests, which is unrequested churn that reduces guardrail coverage on already-working behavior. On balance the stronger invariant placement, the absent-in-S2 membership check, and the reconnect/restart and anonymity proofs make Solution 1 the safer merge.
