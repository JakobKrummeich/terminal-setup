Implement the final voting phase as a vertical slice through every layer.

Participants distribute a fixed budget of five votes over the values that reached this phase; the
facilitator closes the round and starts tiebreak rounds until exactly five values stand.

- A participant intent for casting a vote allocation, routed and persisted the way the existing
  facilitator intent is. Several votes may go on the same value. An allocation that does not use
  exactly the allotted number of votes, targets a value that is not up for vote, or comes from a
  participant who already voted in this round is rejected through the existing rejection mechanism.
- Storage must stay anonymous by construction: tallies and a has-voted marker only, never a row
  that links a participant to a value. Prove it in a test against the stored data.
- Facilitator intents to close the current round and to start a tiebreak round: closing computes
  the standing, and if the fifth place is tied, a tiebreak round over exactly the tied values is
  possible, with the vote budget equal to the number of tied values, repeating until five stand.
  Starting a tiebreak while a round is still open is rejected.
- The phase must not be advanceable until exactly five winning values stand; use the guard
  mechanism this repository already has for that.
- Participant screen: allocate and submit votes, see the remaining budget, and see only the tied
  values during a tiebreak round. Never show individual votes of others.

Acceptance criteria:
- Follow the architecture, naming and layering rules of this repository exactly, including how
  intents, rejections, persistence, guards and pushed state are already done.
- Add tests at the layers this repository tests at, including the anonymity assertion, the tiebreak
  loop with a repeated tie, and every rejection path.
- The existing test suites, the type check, and any coverage or duplication gate still pass.
